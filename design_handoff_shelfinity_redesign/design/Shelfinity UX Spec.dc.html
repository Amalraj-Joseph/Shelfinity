Shelfinity · UX & UI specification · v1.0 · for implementation

A library that reads as a library, not a database.

Shelfinity works. It does not yet feel like somewhere a person goes looking for a book. This document rewrites the whole experience — every screen, including the ones nobody screenshotted — on one visual system, one layout grammar and one set of state rules, so that any screen built later is already designed.

Audience

A coding agent implementing the front end, plus the product owner reviewing direction.

Design system

Modernist — Archivo, flat, zero radius, 2px rules, one red accent. Binding.

Companion file

Shelfinity Screens — live web + mobile mockups of every pattern named here.

Status

Direction locked. Content and role logic to be confirmed against the codebase.

00

How to use this document

Read §1–§9 once: they are the rules. §10 onward is the screen catalogue, and it is deliberately longer than the set of screens that were screenshotted — the point of the rules is that a screen not drawn here can still be built correctly.

Where a spec and a mockup disagree, the spec wins. Where the spec is silent, apply the nearest pattern in §7 rather than inventing one. Never introduce a colour, radius, font or spacing value that is not a Modernist token.

Definition of done, per screen

  1. Uses the app shell and page-header pattern verbatim (§6).
  2. All four data states designed: loading, empty, populated, error (§9).
  3. Status words come from the one vocabulary table (§8) — no new colours for status.
  4. Mobile layout follows the transform rules in §15, not a squashed desktop.
  5. Keyboard reachable; focus ring is the 2px accent ring; no browser-default blue.
  6. Every number on screen is legible without a colour cue.

01

Brief, assumptions, open questions

What I was given

  • 21 screenshots of the live admin account: sign-in, IBM App ID hand-off, dashboard, browse, my activity, users, manage books, reservations, overdue, email config, reports, requests queue with approve/reject dialogs, and two book-tile states.
  • A brief to make it attractive, modern and humane, with web and mobile for each screen.

Assumptions I am designing on

  • One account, capability-scoped. Admin is a role on a normal member account, not a separate app. The member view is this view with the ADMIN group removed — confirmed by the product owner.
  • Catalogue is small-to-mid (hundreds of titles) but must not assume it stays there.
  • Borrowing is request-and-approve, not instant checkout: every borrow and every return passes an admin queue.
  • Reservations exist for unavailable copies and expire on a date.
  • Auth is delegated (IBM App ID); Shelfinity cannot fully restyle that page.
  • Staff work at a desk on a laptop; members are mostly on a phone.

Open questions — do not guess in code

  • Are fines/fees in scope? The spec includes a slot (§11.14) but no policy.
  • Multi-branch or single library? Shelf location assumes one building.
  • Loan length and renewal policy — the UI shows renewals; the rule is unknown.
  • Can the App ID login page be themed, or is it wrapped by a Shelfinity-hosted pre-auth screen (§11.1)?
  • Is there a notification email queue, or is email fire-and-forget?

03

Design principles

Seven rules. When a decision is genuinely open, these decide it — in order.

1 · The shelf comes first

The catalogue is the product; administration serves it. Browsing must be the fastest, richest, most photographic surface in the app — spines, covers, faces, shelves. Every other screen can be plainer than you think.

2 · One question per screen

Each page answers a single question in its first 300 vertical pixels, in words, at display size. "3 books out, 1 due Friday." Numbers on their own are trivia; a number inside a sentence is an answer.

3 · Structure, not decoration

Hierarchy comes from alignment, type size and 2px rules. Not from shadows, not from rounded floating cards, not from tinted backgrounds. If two things are different, make them a different size — not a different colour.

4 · Red is a verb

The accent marks the one action that moves the user forward, the current location, and genuine urgency (overdue). It is never used for decoration and never used twice for the same rank on one screen.

5 · State is always designed

Loading, empty, partial, error and success are first-class layouts, written in advance, in human sentences. A screen without its four states is not finished.

6 · Act, then confirm — reversibly

Approve, reserve, renew and cancel happen immediately with an inline undo. Dialogs are reserved for the irreversible: deleting a title, deleting a person, revoking a role.

7 · Say it like a librarian

Plain, warm, specific, and never in system voice. "Ready for you at the front desk until Tuesday" — not "RESERVATION ACTIVE · EXPIRES 01/09/2026".

Tie-breaker

If two principles conflict, the one with the lower number wins. If a principle conflicts with the Modernist system, the system wins and you raise it as a question.

Role model & information architecture

One account. A role is a set of capabilities layered onto the same person, so the member surfaces never disappear for staff — a librarian is also a borrower. The member experience is literally this app with the library-management group removed from the rail.

MEMBER · everyone

  • Home — my library at a glance
  • Browse — catalogue, search, facets
  • Book detail
  • My Shelf — out, due, requested, reserved, history
  • Lists & saved searches
  • Notifications
  • Profile, card & preferences

LIBRARIAN · adds

  • Desk — today's queue: requests, returns, holds to pull
  • Requests — approve / decline
  • Circulation — check out, check in, renew on behalf
  • Catalogue admin — add, edit, bulk import
  • Reservations & holds
  • Overdue & recalls
  • Members — look up, edit, note

ADMIN · adds

  • Reports & exports
  • Roles & permissions
  • Loan policy — length, limits, renewals, fines
  • Email & notification settings
  • Integrations & auth
  • Audit log

Navigation rule

The rail is two groups, never three: MY LIBRARY always, then MANAGE LIBRARY only if the role grants it, separated by a 2px rule and a group label. Admin-only settings sit under a single Settings entry at the foot of the rail, not as five sibling items. A member's rail therefore has four items and no dividers — it looks like a product, not a truncated CMS.

Geometry

  • Radius 0 everywhere — buttons, inputs, tags, dialogs, avatars, images. No exceptions.
  • Spacing from --space-1…8; page gutters 40px desktop / 20px mobile.
  • Section separation is a 2px rule, not whitespace alone.
  • Shadows only on things that genuinely float: dialogs, menus, toasts (--shadow-lg/md). Panels are flat.

06

Layout system

6.1 · App shell — web (≥1024px)

  • Rail, 240px, --color-surface, full height, 2px right rule. Brand at top on a 2px bottom rule. Items are 40px tall, flush-left label at 14px with a 16px Lucide icon; the current item gets a 3px accent bar on its left edge, accent label, and no fill — no pill, no rounded highlight.
  • Group label (MY LIBRARY / MANAGE LIBRARY) at 11px uppercase, above a 2px rule.
  • Rail foot: the person — name, card number, role tag, and Settings/Sign out. This is where the avatar menu goes; the top bar loses it.
  • Top bar, 64px, 2px bottom rule, holds only: global search (⌘K), notifications, and a role switcher when the account has more than one mode. If a page has no use for it, it still stays — position is memory.
  • Content on --color-bg, 40px gutters, max content width 1240px, left-aligned inside a 12-column grid with 24px gutters.

Page header pattern — mandatory, identical on every page

  1. Row of context: breadcrumb or group label (11px upper), and page-level actions pushed right.
  2. Page title, 42px.
  3. Answer line, 20–25px, one sentence, states the page's finding in plain words. Not a description of the page.
  4. 2px rule.
  5. Then, and only then, controls (search, tabs, filters) — never above the title.

Example, Overdue: title "Overdue", answer line "Nothing is overdue. 4 loans come due this week." — the same slot carries good news and bad.

6.2 · App shell — mobile (<768px)

  • Rail becomes a bottom tab bar, 56px + safe area, 2px top rule, max 4 tabs: Home, Browse, Shelf, More. Staff get Desk in place of Shelf, with Shelf inside More.
  • Current tab: accent icon + accent label + 2px accent bar along the top edge of the tab. Never a filled pill.
  • Top bar collapses to a 52px header: page title at 20px, one action, and back chevron when deep.
  • All targets ≥44px. Row actions become a full-width sticky action bar or a bottom sheet — never a 24px icon in a table cell.
  • Tablet 768–1023px: rail collapses to a 64px icon rail with tooltips; content keeps desktop layout at 2 columns.

09

Cross-cutting patterns

9.1 Loading

  • First paint of a route: skeletons in the real geometry, page header rendered immediately with the title (it is known).
  • Refetch of existing data: keep the data, show a 2px accent progress line under the top bar. Never dim, never spinner-over-table.
  • A single row acting: that row's action becomes a 14px inline "Working…" label; the row stays readable.
  • Nothing blocks the whole screen after first paint, ever.

9.2 Empty

  • Three flavours, each with its own copy: nothing yet (invite), nothing matched (offer to relax the filter), nothing left (congratulate — Overdue at zero reads "Nothing overdue. The shelves are square.").
  • Always name the next action, always left-aligned inside the panel that would have held the data.

9.3 Error

  • Inline where the failure was caused; page-level only when the page cannot render.
  • Say what failed, what is intact, what to do. Offer Retry. Never surface a stack, a code or the word "error" alone.
  • Field errors: beneath the field, accent-700, with the fix ("Port must be between 1 and 65535").

9.4 Actions — optimistic and reversible

  • Approve / Decline act on click. The row restyles at once, a toast offers Undo for 8s. The optional remark moves into the toast ("Add a note") and into the request detail — it never gates the decision. Decline requires a reason, chosen from a 4-item list with an optional note, shown as an inline expansion of the row, not a modal.
  • Reserve / Cancel / Renew act immediately with undo.
  • Delete a title, delete a member, revoke a role use the dialog (§7.12) and require typing nothing — but they name the consequence and cannot be undone by toast.
  • Bulk: selecting rows raises a bar with the count and the two or three verbs that apply; bulk approvals are undoable as one batch.

9.5 Notifications & email

  • Every state change that affects a member produces one notification, and email templates share the copy in §14 — the in-app notification and the email say the same sentence.
  • Notification list groups by day, unread marked by a 3px accent left bar, "Mark all read" as a ghost action.

9.6 Search everywhere

  • ⌘K from anywhere: titles, people (staff only), and page jumps in one list, keyboard-first.
  • Every table with more than 20 rows gets its own scoped search; the placeholder names the searched fields.

Screen specifications

11.1 · Sign in /signin · public

Web

Two columns, no gradient. Left 58%: a grayscale photograph of a real reading room, full-bleed, with the wordmark top-left and a poster statement over the lower third — "Every book in this building, from wherever you are." Right 42% on --color-bg, flush left, 96px gutter: 42px "Sign in", one sentence of what happens next, a primary Continue, a secondary "Sign in with your institution", and a ghost "Request a library card". Foot: branch, hours, telephone — three facts that prove the library exists.

The App ID hand-off cannot be fully themed. Mitigation: state it before the jump ("You'll finish signing in on our identity provider") so the change of skin is expected rather than alarming, and pass the return URL so the jump back lands on Home, not the sign-in page. If theming is possible, apply ground, Archivo, zero radius and the accent button, and remove the default-configuration warning before launch.

Mobile

Photograph as a 38vh top band with the statement over it, actions stacked full-width beneath, 44px tall, primary first. Hours and phone collapse to one line. No scroll needed to reach Continue.

States

  • Idle · redirecting ("Taking you to sign in…" with the accent progress line) · returned-with-error ("That link expired. Try again." + Continue) · signed-out-just-now ("You're signed out. Your shelf is safe.")

11.2 · Join / request a card /join · public · new

The screenshots show USER REGISTRATION requests arriving in the admin queue, so a registration surface exists but was never designed. Web: FormPanel (§7.13) at 560px — name, email, address, membership type radio — beside a "What happens next" Timeline (§7.14): You send this → a librarian checks it, usually within a day → your card number arrives by email → you can borrow immediately. Mobile: the same form, single column, the timeline moved beneath the submit as reassurance. Success is a page, not a toast: "Sent. We'll email you at amalraj@… when your card is ready." States: pristine, invalid (field-level), submitting, sent, already-a-member (offer sign in).

11.3 · Home / · member

Web

  • Page header: context "MY LIBRARY", title "Good afternoon, Amalraj", answer line "You have 3 books out. 1984 is due Friday." — the answer line is generated from data and is the whole point of the page.
  • Then a "What you have out" list: one row per loan, cover thumb 40×60, title, author, DueMeter (§7.15), day-named due date, and Renew / Return actions inline. This replaces the four counters as the top-of-page content.
  • Right column, 320px: Waiting on the library (requests + holds, each with a plain sentence) and Your card (number, member since).
  • Below a 2px rule: "Back on the shelf this week" — a 6-tile shelf of just-returned titles, and "Because you borrowed 1984" — a 6-tile recommendation shelf. Browsing starts on Home.
  • Counters, if wanted at all, sit at the very foot as a single FigureBlock band. They are trivia, not the headline.

Mobile

  • Greeting + answer line, then the loans list as full-width rows with the DueMeter under the title; actions in a swipe-free trailing row of two 44px buttons.
  • Waiting-on-the-library becomes a single accent-barred strip above the loans when non-empty; hidden when empty.
  • Shelves scroll horizontally, 128px-wide tiles, snap. Card lives in More.

States

  • New member, nothing out: answer line becomes "Your shelf is empty — the catalogue isn't." with a primary Browse and the two shelves promoted up.
  • Overdue present: answer line leads with it, in accent. One overdue item outranks everything else on the page.
  • Loading: header renders, three skeleton loan rows.
  • Staff account: an extra strip at the very top — "12 requests are waiting at the desk" → Desk.

11.4 · Browse the catalogue /books · member

Web

  • Grid of BookTiles (§7.4): 5 columns at 1440px, 4 at 1200, 3 at 1024. Covers are the majority of the tile — this is the one screen that is mostly image.
  • Sort control right of the result count: Relevance · Recently added · Title · Most borrowed.
  • Above the grid when no search is active: three curated rails — "New this month", "Most borrowed", "Staff picks" — then the full grid under a rule. Browsing beats searching for people who don't know what they want.
  • Infinite scroll with a "Load more" fallback and a persistent count; the URL carries facets so a search is shareable and savable ("Save this search").

Mobile

  • Sticky search + a single "Filter" button showing the applied count; facets open as a bottom sheet with Apply/Clear at the foot.
  • 2-column tile grid, covers 2:3, one 44px action per tile. Rails scroll horizontally.

States

  • Skeleton tiles on first load (12).
  • No results: "Nothing matched dune messiah." + the two nearest suggestions + "Ask us to buy it" + Clear filters. Never a bare centred "No rows".
  • Facet returns zero: disable the option and show its count as 0 rather than letting the user reach an empty grid.
  • Search error: keep the last results, show an inline retry strip.

11.5 · Book detail /books/:id · member · new

The most conspicuous gap: today a member decides from a 3-line tile. Web: cover 320px wide in grayscale on the left; right column holds title at 42px, author as a link to their other titles, the availability sentence at 25px ("2 of 3 copies on the shelf"), the primary action, then the blurb, then a facts table (ISBN, publisher, year, pages, language, subjects as tags, shelf location — "Floor 2 · Bay 14 · Fiction OR"). Imagery — the humane part

Photography is the only thing that will make Shelfinity feel like a place rather than a database, and it is strictly rationed: five surfaces, one photograph each, always through .grayscale, always at zero radius, never tinted, never behind text without a solid ink scrim.

WhereSubject to shoot or licence
Sign inThe reading room, wide, from the door, with people in it and no faces identifiable.
JoinTwo hands passing a card across the desk.
Home, first-run onlySomeone crouched at a low shelf, reading a spine — the moment of looking for a book.
Browse, "Staff picks" railA librarian's hands on a small stack, on the desk.
Reports header (print)The stacks, empty, early morning.

Everywhere else the imagery is book covers, which are already photographs of a kind. Covers do more humanising work per pixel than any stock photo.

Rules

  • Real, or nothing. Use the library's own building and staff. No stock smiling students, no AI-generated shelves, no illustration set.
  • Missing cover → a flat spine block: ground --color-neutral-200, title in Archivo 800 rotated as on a spine, author beneath. Never a grey box with a broken-image glyph.
  • Photographs never carry meaning that isn't also in text. A member on a slow connection loses nothing.
  • Alt text describes the room, not the mood: "The main reading room, looking toward the tall windows."
  • Covers: 2:3, object-fit cover, grayscale, with a 1px divider edge so pale covers keep an edge on the ground.
  • In the mockups these are drop-in placeholders — replace them with the library's photographs before launch.

14

Accessibility & interaction states

Non-negotiable

  • Body copy on ground ≥ 4.5:1 — use --color-accent-700 for accent-coloured text, never --color-accent at 14px.
  • Status is word-first; colour is redundant everywhere.
  • Focus: 2px accent ring, 2px offset. Visible on every interactive element including table rows and tiles.
  • Targets ≥ 44px on touch, ≥ 32px on pointer.
  • Tables get real <th scope>, captions, and row-level action labels that name the row ("Approve Amalraj's request for 1984").
  • Dialogs trap focus, restore it on close, and are labelled by their title.
  • Toasts announce via aria-live="polite"; errors via assertive.
  • Respect prefers-reduced-motion: skeleton pulse and any transition drop to none.

Motion budget

  • 120ms for state changes on the element you touched (tag swap, row restyle).
  • 180ms for entering surfaces (sheet, dialog, toast), ease-out, translate only.
  • No page transitions, no parallax, no animated numbers. Modernist doesn't move much.
  • The only looping animation in the product is the skeleton pulse and the 2px accent refetch line.

Keyboard

  • ⌘K global search · / focuses the page's search · g then h/b/s/d jumps to Home/Browse/Shelf/Desk.
  • In the requests queue: j/k move, a approve, d decline, u undo. Staff live in this table.
  • Escape closes the topmost surface only.

16

Notes for the implementing agent

Order of work

  1. Tokens first. Replace the current theme with Modernist's styles.css variables. Delete every hard-coded hex, every border-radius, and the gradient. Nothing else starts until this lands.
  2. Shell. NavRail with the two-group role rule, top bar, PageHeader. Every route adopts it before any route is redesigned.
  3. Primitives. §7.1–7.16 as components with all listed states, including skeletons and empty states, built in from the start.
  4. Status vocabulary. One module exporting the §8 mapping; no component invents a status label or colour.
  5. Member path: Home → Browse → Book detail → My Shelf. This is where the product is judged.
  6. Staff path: Desk → Requests (with optimistic actions and bulk) → Circulation → Catalogue.
  7. Admin path: Reports → Settings sections.
  8. System pages, notifications, email templates last — but before launch, not after.

Rules that are easy to break by accident

  • No border-radius. Anywhere. Including avatars and images.
  • No new colour. If you reach for green or amber, you have missed §8.
  • No spinner over existing content.
  • No modal for anything reversible.
  • No UUID, HTTP code or field name in user-facing copy.
  • No centred text — headings, empty states and button labels are flush left.
  • No dashboard whose first row is four counters.
  • Every table needs its filtered-empty state written, not just its empty state.

Acceptance checklist per route

Shell ✓ · PageHeader with an answer line ✓ · four data states ✓ · statuses from §8 ✓ · mobile per §15 ✓ · keyboard + focus ✓ · copy passes §13 tone ✓ · no token violations ✓.
